The stage UI plays audio, a vanished audio device is actually noticed, and the
demo is long enough to measure dropouts with. All three came out of testing on
the band's laptop.

## btui plays

Loading a set list and a `device.json` into the UI, pressing play and hearing
nothing was correct behaviour — the transport was simulated and the title bar
said so — and it was still the wrong behaviour. Taking a `--device` argument,
reading the file and then never opening a device is misleading whatever the
title says.

`btui` now drives a real player through a real device. Bar and beat on screen
come from the same tempo map the click is generated from, so the number you
read and the click you hear cannot disagree. The simulated transport remains
for the two cases that need it — rendering screens on a machine with no audio,
and building a set list with the interface unplugged — and which one is
running is in the window title and printed at startup.

## A device that disappears is noticed

Pulling the USB cable mid-song used to do nothing at all: the playhead froze,
no message appeared, and the program sat there until Ctrl-C. On stage that is
the music stopping with a frozen screen and no explanation.

The detection asked PortAudio whether the stream had errored. WASAPI reports
no error for an unplugged interface — the callback simply stops being called
and the stream still claims to be active. The signal is the absence of
callbacks, not the presence of an error, and both `btplay` and `btui` now
watch for it.

## A demo worth measuring with

`btrender --make-demo` wrote eight-second stems, which is fine for checking
routing and useless for counting dropouts: a machine that drops a buffer three
times in ten minutes reads zero over ten seconds. Stems are two minutes by
default now, with `--seconds` to choose otherwise.

## Also

- The editor's save button is disabled, with the reason, when there is nowhere
  to save — rather than appearing to work on the built-in demo set.
- Corrected throughout: the UMC404HD exposes a **four-channel** `OUT 1-4`
  endpoint under WASAPI. Earlier documents claimed Windows splits it into two
  stereo endpoints and that four-output routing required ASIO. That came from
  forum posts rather than measurement and was wrong. ASIO is worth having for
  exclusive access and lower latency; it is not a prerequisite.

## Still not done

No waveform alignment, no MIDI or footswitch, no routing editor in the UI.
Dropout behaviour across buffer sizes is still unmeasured. macOS and Linux
build and pass their tests, and nobody has run them.
